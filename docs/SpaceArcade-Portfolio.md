# 우주 오락실 (Space Arcade) — 실시간 멀티플레이어 미니게임 플랫폼

| 항목 | 내용 |
| --- | --- |
| 기간 | 약 7주 |
| 팀 구성 | 6인 |
| 맥락 | SSAFY 자율 프로젝트 |
| 담당 역할 | 배포/CI·CD 및 운영 인프라 구축 · 시스템 아키텍처 설계 · 미니게임 2종 개발 |

닉네임만 입력하면 최대 100명이 동시에 접속해 여러 미니게임을 라운드로 진행하고, 라운드별 순위 점수를 누적해 최종 랭킹을 가리는 마리오 파티형 실시간 경쟁 플랫폼. 카훗의 접근성과 테트리스 99의 경쟁감을 결합하는 것을 목표로 했다.

---

## 1. CI/CD 파이프라인 구축 (핵심 담당)

GitLab–Jenkins–Docker로 빌드부터 배포까지 전 과정을 자동화했다. master 브랜치에 MR이 머지되면 Jenkins가 변경을 감지하고, 서버에서 코드를 강제 동기화(`git fetch && git reset --hard`)한 뒤 백엔드·프론트엔드 Docker 이미지를 빌드하고 `docker compose up -d --build`로 전체 스택을 재배포하는 흐름이다. 배포 완료 시 Mattermost로 팀에 자동 알림이 가도록 연동해, 6명이 병렬로 개발하는 환경에서 통합·배포가 병목이 되지 않게 했다.

특히 단일 서버가 아니라 **SSAFY 서버와 C5a 서버 두 대에 동시 배포**하도록 구성했다. Jenkins가 로컬 배포를 수행한 뒤 SSH로 C5a 서버에 원격 배포까지 트리거해, 멀티 서버 환경에서도 한 번의 머지로 양쪽이 같은 버전을 유지하도록 했다.

**자동화 흐름**

1. GitLab push → Jenkins 감지
2. 서버 코드 강제 동기화 (`git fetch && git reset --hard`)
3. 백엔드 / 프론트엔드 Docker 이미지 빌드
4. `docker compose up -d --build`로 컨테이너 재시작
5. C5a 서버 SSH 원격 배포 트리거
6. Mattermost 배포 완료 알림 발송

## 2. 멀티 서버 로드밸런싱 및 운영 인프라 (핵심 담당)

100명 동시 접속을 두 서버로 분산하기 위해 Nginx 리버스 프록시 기반 로드밸런서를 직접 구축하고, 두 서버 간 로드밸런싱 아키텍처를 설계했다. 분배 정책으로 `ip_hash`를 선택한 것이 핵심인데, 이 서비스는 WebSocket 기반 실시간 통신이라 같은 클라이언트가 매 요청마다 다른 서버로 가면 연결이 끊긴다. `ip_hash`로 동일 클라이언트를 같은 서버에 고정(sticky)시켜 WebSocket 세션 일관성을 보장하면서 부하는 두 서버로 분산했다.

여기에 운영 환경에 필요한 요소를 함께 구성했다. Let's Encrypt로 SSL 인증서를 발급해 전 구간 HTTPS를 적용했고(WebSocket도 wss로 보안 연결), Prometheus + Grafana로 JVM·CPU·응답시간·동시 접속자 수를 실시간 모니터링하는 대시보드를 만들어 부하 상황을 가시화했다.

**구축 항목**

- Nginx 리버스 프록시 + 로드밸런서 (SSAFY + C5a 두 서버 `ip_hash` 분배)
- Let's Encrypt SSL — 전 구간 HTTPS / WebSocket wss 보안 연결
- Prometheus + Grafana 모니터링 — JVM, CPU, 응답시간, 동시 접속자 수
- 두 서버 간 로드밸런싱 아키텍처 설계 및 구축

## 3. 플러그인 기반 게임 모듈 아키텍처 설계 (설계 주도)

게임이 3종에서 N종으로 언제든 늘어날 수 있도록, 각 미니게임을 독립 모듈로 개발하되 공통 `IGameModule` 인터페이스를 따르도록 표준화했다. Shell(플랫폼 본체)이 게임 내부 구현에 의존하지 않고 `onReady` / `onProgress` / `onComplete` 콜백만으로 게임을 마운트·언마운트·점수 집계하는 구조다. 게임 레지스트리 패턴으로 신규 게임을 등록만 하면 플랫폼에 자동 편입되게 설계해, 팀원들이 각자 게임을 병렬 개발해도 충돌 없이 통합되도록 했다.

---

## 4. 무(無)DB 휘발성 상태 + 실시간 동기화 구조 설계 (설계 참여)

게임 데이터가 영구 저장될 필요가 없다는 판단 아래 DB를 두지 않고, 서버 메모리와 Redis만으로 방·게임·순위 상태를 관리하는 구조를 채택했다. 실시간 순위는 매 프레임이 아니라 **200ms 델타 동기화**로 변경분만 브로드캐스트해, 100명 동시 접속 환경에서도 네트워크 부하를 억제하면서 '추월당하는 느낌'을 살렸다.

> Redis Pub/Sub 멀티 인스턴스 브로커와 WebSocket 서버 구현은 백엔드 팀원이 맡았고, 본인은 아키텍처 의사결정과 무DB 설계 논의에 참여했다.

## 5. 미니게임 2종 직접 개발

**단어 외우기 (고대 유적 테마)** — 30초 암기 + 60초 입력의 기억력·타이핑 게임. 이미 맞힌 단어 중복 체크를 `Set` 자료구조로 O(1)에 처리했고, 단계 전환은 CSS transition으로 연출했다.

**총알 피하기 (우주 테마)** — `requestAnimationFrame` 기반 게임 루프에 delta time을 적용해 **프레임 독립적(frame-independent)으로 처리**, 어떤 기기에서도 공정한 난이도가 되도록 했다. 총알 200개를 **오브젝트 풀링**으로 재사용해 GC 부하를 줄였고, 충돌 판정은 제곱근을 생략한 거리 비교(`dx*dx + dy*dy < (r1+r2)²`)로 최적화했다.
